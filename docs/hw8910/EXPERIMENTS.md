# Воспроизведение инцидентов на исходном прототипе

Основа: прототип 3099a59, Python 3.12 (/opt/anaconda3/bin/python3.12). Реализации lab.py, release.py, service.py при опыте не изменялись. Входы — автоматически созданные STUB ONLY A/B. Результаты не являются оценкой качества модели.

Команда воспроизведения из корня репозитория:

```sh
/opt/anaconda3/bin/python3.12 -m unittest discover -s tests_hw8910 -p test_incidents.py -v > docs/hw8910/evidence/incidents-before.log 2>&1
```

Каждый test получает новый TemporaryDirectory/workspace и выполняет lab.py init в отдельном процессе. Серверам назначается свободный порт ядром; HTTP-запросы реально проходят через localhost. Сервер и поток закрываются в finally, временные файлы удаляются cleanup. На этом стенде sandbox запрещал bind, поэтому подтверждающий запуск выполнен с разрешением локального HTTP. Итог: 10 tests, 20 assertion failures, 0 errors; exit code 1.

SHA-256 указателя в обоих опытах 2: до `aca0bc1332936349f868b84d800dec94e1a042f4aec3196fe4c4c031c3b5c6d1`, после `0bb6ec1a07f2c71016d90b62af8865121cb2b7b4bc8d6cd5d0336af99ad0a7d3`. Они также напечатаны в журнале.

Идентичность результата подготовки зависит от содержимого данных и всей конфигурации; идентификатор попытки меняется при повторном запуске и не должен инвалидировать устойчивый кеш. Идентичность выпуска включает модель, runtime, протокол и оценку: один model_id недостаточен. Помимо passed проверяются статус завершённости, типы, обязательные поля, конечные метрики и совместимость всех хешей с manifest; runtime_sha256 пересчитывается из канонического runtime. Реальные файлы требуют отдельной проверки хешей до публикации и загрузки.

В задаче 2 исправлений нет. В defects.csv fix_commit и after_log оставлены pending до фактического исправления и подтверждающего запуска. Ошибка диска полностью моделируется mock; заполнения настоящего диска нет. Проверка ошибки записи теперь внедряет OSError в os.fsync временного файла, поэтому совместима с корректной атомарной записью через fdopen/NamedTemporaryFile. Старый прототип fsync не вызывает и падает на assertRaises.

После review добавлены test_04b и test_04c. Первый публикует три выпуска одного model_id: исходный, изменённый runtime (с новым каноническим runtime_sha256 и согласованным отчётом), новую оценку при том же runtime. Каждый выпуск повторяется отдельным subprocess: ожидаются три события, фактически шесть. Дедупликация только по model_id дала бы одно событие, по model_id+runtime — два; обе ошибки тест обнаруживает. Второй инъецирует исключение после успешного publish, до append журнала в run; указатель уже B. После двух subprocess-повторов ожидается ровно одно согласованное событие, фактически два. Инъекция выполняется на границе release.publish/lab.run и не требует заполнения диска.
