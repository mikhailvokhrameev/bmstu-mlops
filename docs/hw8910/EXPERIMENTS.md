# Воспроизведение инцидентов на исходном прототипе

Основа: прототип 3099a59, Python 3.12 (/opt/anaconda3/bin/python3.12). Реализации lab.py, release.py, service.py при опыте не изменялись. Входы — автоматически созданные STUB ONLY A/B. Результаты не являются оценкой качества модели.

Команда воспроизведения из корня репозитория:

```sh
/opt/anaconda3/bin/python3.12 -m unittest discover -s tests_hw8910 -p test_incidents.py -v > docs/hw8910/evidence/incidents-before.log 2>&1
```

Каждый test получает новый TemporaryDirectory/workspace и выполняет lab.py init в отдельном процессе. Серверам назначается свободный порт ядром; HTTP-запросы реально проходят через localhost. Сервер и поток закрываются в finally, временные файлы удаляются cleanup. На этом стенде sandbox запрещал bind, поэтому подтверждающий запуск выполнен с разрешением локального HTTP. Идентичность результата подготовки зависит от содержимого данных и всей конфигурации; идентификатор попытки меняется при повторном запуске и не должен инвалидировать устойчивый кеш. Идентичность выпуска включает модель, runtime, протокол и оценку: один model_id недостаточен. Помимо passed проверяются статус завершённости, типы, обязательные поля, конечные метрики и совместимость всех хешей с manifest; runtime_sha256 пересчитывается из канонического runtime. Реальные файлы требуют отдельной проверки хешей до публикации и загрузки.

В задаче 2 исправлений нет. В defects.csv fix_commit и after_log оставлены pending до фактического исправления и подтверждающего запуска. Ошибка диска полностью моделируется mock; заполнения настоящего диска нет. Проверка частичного Path.write_text дополнительно демонстрирует конкретный способ порчи исходного прототипа; при переходе на другой способ записи fault-injection следует адаптировать к используемому примитиву, сохраняя проверку неизменности старых байтов.
